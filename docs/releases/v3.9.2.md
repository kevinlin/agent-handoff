# v3.9.2: Identity sections drop the dual-host prefix

Identity sections in `config.toml` carried a prefix from the dual-host era: `[hosts.claude_code.identities.deep_reasoner]`. Only one host is left, so the prefix names nothing. This release removes it. The section is now `[deep_reasoner]`, and likewise `[fast_worker]`, `[arbiter]`, `[e2e_specifier]` and `[e2e_verifier]`. Fields, field order, `[review]`, `[routing]` and `schema_version = 2` are unchanged.

## What changes in the file and the CLI

`handoff-config.py get` and `resolve` keys drop the prefix too, so the key is `deep_reasoner.backend`. The old key, `hosts.claude_code.identities.deep_reasoner.backend`, no longer resolves, and no alias exists. Validation messages read `deep_reasoner.backend must be one of ...`.

## What happens to your existing file

A file written before 3.9.2 still loads with the same values. Reading never rewrites it. That covers `resolve`, `get`, `validate`, delegation and opening the wizard.

The next config write re-emits every identity section bare, in the place where the first one stood. The writes are `handoff-config.py set` and `set-review`, setup apply, smoke's verification write, and `--uninstall --remove-config`, which clears both forms. Every other section keeps its bytes, including the preamble and stale `hosts.codex.*` blocks. As before, comment lines inside an identity section are not kept. That includes a comment sitting just before the next header, because it belongs to the section above it.

A file that defines one identity twice is refused, and the error names both headers. That includes one identity defined in both forms. Delete one of the two sections by hand. Two different identities in different forms load fine. A legacy header that names an unknown identity is still refused, and `[hosts.<host>.roles.*]` from schema v1 is refused as before.

## Known gaps

- An engine older than 3.9.2 reads only the prefixed headers. It sees the bare sections as unknown sections, so the identities in that file are invisible to it. If no other layer configures a role, `delegate-codex.sh` refuses it. If the global config still has a legacy-form identity, the old engine runs the global values, and `config_source` still says `project`. That case does not fail closed. When a pre-3.9.2 engine writes to a migrated file, one identity can end up in both forms. 3.9.2 then refuses the file until you delete one section.
- A misspelt bare header such as `[deep_reasonr]` is an unknown section, so `validate` does not catch it. It round-trips untouched, and that identity is absent from the file. Resolution uses the next layer instead: if the global config defines the identity, the global values run. `delegate-codex.sh` refuses the role only when no layer configures it.
